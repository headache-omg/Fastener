# Fastenerの工夫点と改善（1.2.3）

## 何を独自に作っているか

Fastenerは、Zstandard（Zstd）とLZ4を使う圧縮・展開ツールです。
圧縮コーデック自体を新しく発明したものではありません。独自の工夫は、
データの分割方法、並列処理の組み合わせ、メモリ使用量の管理、書庫形式、
破損検出と認証付き暗号化にあります。

## 1. データの変化を見て分割位置を決める

入力を4 KiBごとのブロックとして見て、各ブロックの16バイトおきの値を採点します。
直前のブロックとの差と、同じブロック内のサンプルの変化を合計し、変化の大きい
位置を分割候補にします。目標チャンクサイズの付近から、点数の高い境界を選びます。

例えば目標8 MiBなら、原則として8 MiB付近の探索範囲から切れ目を選びます。
末尾は残りを1つのチャンクにします。ファイルの解析は64 MiBの区間ごとです。
これは内容に応じた境界のヒューリスティックであり、文書の意味を理解しているわけでも、
一般的なローリングハッシュ方式のCDCと同じ方式でもありません。

**狙い**は、性質が異なるデータの境目付近で分割し、各チャンクを扱いやすくすることです。
ただし、固定長分割より圧縮率や速度が必ず良くなるとは限りません。採点には追加の時間が
かかりますし、分割するとチャンクをまたぐ辞書の共有ができなくなります。

同じ入力・Zstd level 1・15ワーカーで比較するプログラムを
`examples/compare_boundaries.rs` に用意しました。固定長分割と内容に応じた分割を交互に実行し、
採点時間・圧縮時間・推定FSTサイズ・復元一致を記録します。

```powershell
cargo run --release --example compare_boundaries -- sample.bin 5 8388608
```

これは**メモリ上で分割方式を比較する実験**です。ファイル入出力、通常のファイルAPIの
バッチ制限、暗号化は含めません。初回（iteration=0）はウォームアップです。
出力の `estimated_fst_bytes` は既存形式のヘッダーとレコード長を加えた値で、
実際の書庫ファイルは作りません。結果は `benchmarks/v1.1.0/` に保存します。

## 2. チャンクを独立させて並列化する

分割したチャンクはRayonのワーカーで並列に圧縮・展開します。処理終了順にかかわらず、
書き込みは元の順番を保ちます。1つの大きな圧縮ストリームを途中で無理に分割するのではなく、
最初から独立して復元できる単位として保存する方法です。

CPUの数、メモリ帯域、ストレージ、データの性質によって効果は変わります。
チャンク数が少ない入力では、多数のCPUを十分に使えません。

## 3. 圧縮して大きくなったデータはそのまま保存する

FastはLZ4、BalancedはZstd level 1、DenseはZstd level 12を使います。
圧縮後のペイロードが元データより小さくならない場合は、元データをそのまま格納します。
JPEGなどの圧縮済みデータや乱数では、この処理により膨張を抑えます。

ただし「事前に圧縮可能性を完全に見抜く」処理ではありません。一度圧縮して比較します。
書庫ヘッダー、ハッシュ、暗号化時の認証タグのぶんは追加されます。

## 4. CPUとGPUを用途に応じて使い分ける

GPUが担当するのは境界の採点です。Zstd/LZ4による圧縮そのものや暗号化をGPUで行うわけではありません。
大きい入力では、各ブロックのサンプルをCPUとGPUで分担し、採点結果を合成します。

1.1.0では次の順序で不要な作業を避けます。

1. 空の入力なら解析しない。
2. 区間の長さが目標サイズの2倍以下なら分割不要なので、採点自体をしない。
3. **入力ファイル全体が16 MiB未満なら、分割が必要でもフルCPU採点だけを実行する。**
4. それ以外では既存のCPU/GPU複合解析を使い、GPUが利用できない場合はCPUに切り替える。

小さなチャンクサイズを指定した小容量ファイルでも、GPU初期化・転送・読み戻しが発生しなくなります。

1.1.1では、GPUへの転送を「採点で実際に参照する16バイトおきの1バイト」に絞りました。
64 MiBの解析区間なら、入力転送は64 MiBから4 MiB＋長さ情報4バイトになります。
末尾の実サンプル数も渡し、パディングを採点しないため、境界選択の意味は変えません。
CPU側は256ブロック以上の場合にRayonで並列採点します。小さい区間は逐次処理のままです。
暗号化の鍵導出条件やチェックサム検証は弱めていません。
[1.1.1の速度比較](../benchmarks/v1.1.1/REPORT.md)に効果と測定条件を記録しています。
16 MiBは現時点の運用上のしきい値で、すべての機器での最適値を証明したものではありません。
フォルダーでは内部の各ファイルのサイズで判断します。

## 5. 大きいファイルでメモリを使い切らないようにする

暗号化なしのファイル処理はメモリマッピングを利用し、処理対象のチャンク数とデータ量で
バッチを制限します。rawチャンクの展開・検証では、余分な複製を避けてマッピングを参照します。
大きい全体ハッシュの計算にも並列処理を使います。

1.2.2では、FSTファイルの圧縮中、Zstdの作業領域をワーカーごとに再利用します。
チャンクごとに作業領域を作り直すコストを減らすためです。圧縮しても小さくならない
チャンクは、入力マッピングをそのまま参照して書き込みます。従来のように同じ大きさの
バッファをもう一つ作る必要がありません。Zstdで縮まらなかった場合の出力用バッファも
ワーカー内で再利用します。128 MiB以上のファイルでは、全体ハッシュ計算と境界解析を
並行して進めます。バッチ制限と一時ファイルへの書き込み、
チャンク・ファイル全体のハッシュ検証は維持しています。
これは**暗号化なしの単一ファイルFST経路**の改善で、暗号化・ZIP・フォルダー束の
速度向上まで示すものではありません。書庫のバイト列も従来版と同じです。
[大容量ファイルの実測](../benchmarks/v1.2.2/REPORT.md)に条件と結果を記録しました。

1.2.3では、暗号化なしの単一ファイルFSTを展開するとき、出力先と同じ場所に作る
一時ファイルをメモリマッピングします。重ならない出力領域へチャンクを並列に直接展開し、
各チャンクのBLAKE3を検証します。従来の「チャンクを別バッファへ展開してから順番にコピー」
する処理を省きます。最大256 MiBのバッチを展開した直後に全体ハッシュへ加えるため、
50 GiBをすべて書き終えてから再読込することも避けられます。最後の全体ハッシュが一致した
場合だけ一時ファイルを公開します。メモリマッピングはファイルサイズ分の仮想アドレスを
予約しますが、ファイル全体をヒープに読み込む方式ではありません。
[2 GiBと50 GiBの比較](../benchmarks/v1.2.3/REPORT.md)を参照してください。

暗号化版は64 MiBまでの入力区間を読み、1チャンク最大16 MiB、最大8レコードずつ
暗号化・復号・展開を処理します。ファイル全体をメモリに読み込まず、平文の中間書庫も作りません。
コーデックの作業メモリ、Argon2idの64 MiB、暗号文と復元バッファなどは別途必要です。
「常に合計256 MiB以内」などの絶対的な上限を保証するものではありません。

## 6. 破損検出と秘密の保護を区別する

暗号化なしのBLAKE3チェックサムは、偶発的な破損の検出に使います。
第三者がデータとチェックサムの両方を書き換えることまでは防ぎません。

任意の暗号化では、パスワードからArgon2idで鍵を作り、圧縮済みの各チャンクを
XChaCha20-Poly1305で暗号化・認証します。Rayonはこれらの処理を並列に実行するために使います。
暗号のアルゴリズム自体はRustCryptoの実装を使用します。

内部のファイル名、ファイルサイズの値、内容、全体ハッシュも暗号化します。
チャンクの位置とヘッダーを認証に結び付け、順番の変更、欠落、別書庫からの差し替えを検出します。
詳しい形式・制限・パスワードの扱いは[暗号化仕様.md](暗号化仕様.md)に記載しています。

## 7. 失敗時に既存データを失わない

出力は一時ファイルに書き、必要な検証がすべて成功してから公開します。
暗号化されたフォルダーの展開も一時ディレクトリに行い、全体の認証後に移動します。
パスワード違いや破損時には、既存の出力を置き換えません。

これは電源断への完全な耐久性や、平文一時ファイルの安全な消去を保証するものではありません。
元ファイルを作業中に変更しないことも必要です。

## 8. 任意のリカバリーレコード

チェックサム・認証は「壊れたことを検出する」仕組みです。壊れたデータを復元するには、
別途、冗長な復旧データが必要です。

完成した書庫に対して作る**任意の外部復旧ファイル**を採用しました。
大容量では約10%の復旧データに端数・索引分が加わり、既存の書庫形式は変更しません。
1.2.0ではこの方式を実装しました。20データ片＋2復旧片、4 KiB〜1 MiBの可変粒度、
各片のハッシュとヘッダー・索引の二重化を採用しています。修復後は全体ハッシュと
元の書庫検証を行い、暗号化書庫では認証も通してから別ファイルへ確定します。
詳細と対応範囲は[リカバリーレコード仕様](リカバリーレコード案.md)に記載しています。

## 9. 復旧計算を並列化する

1.2.1では、Reed–Solomonの計算が片の同じバイト位置ごとに独立することを利用し、
256 KiB以上の片を64 KiB単位の区間に分けて並列計算します。元の配列の重ならない部分を
参照するため、並列化用に書庫データ全体を複製しません。小さい片は逐次処理を維持します。
片ごとのハッシュと大きな全体ハッシュ更新も並列化し、最大22 MiBの片バッファを
グループ間で再利用します。末尾の余りは毎回ゼロ埋めし、前のグループの内容が残らないようにします。
旧版との復旧ファイル一致、修復後の全体ハッシュ、書庫検証・暗号認証は維持しています。
[速度・メモリ使用量の比較](../benchmarks/v1.2.1/REPORT.md)を参照してください。

## 説明時に使える要約

「FastenerはZstd/LZ4を土台とし、内容に応じたチャンク分割、チャンク単位の並列処理、
小容量時の解析省略、メモリ使用量の管理を組み合わせた書庫ツールです。
独自の圧縮コーデックを発明したという主張ではありません。
破損検出に加え、任意の認証付き暗号化を実装し、実測と復元一致テストで動作を確認しています。」
